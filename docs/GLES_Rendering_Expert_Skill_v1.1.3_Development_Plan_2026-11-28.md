## 1. 先明确本版要交付什么

### 1.1 面向使用者的五个结果

1. **能读懂项目。** 识别引擎、版本、实际 backend、构建入口、线程和资源所有权；不确定的信息明确保留为未知。
2. **能找到下一步。** 从画面、日志、生命周期或性能问题中选择必要的检查；证据不足时给一个有成本上限的探测任务。
3. **能验证建议。** 将合法候选关联实际 GLES 实验；先确认画面和业务功能正确，再比较性能、内存或延迟。
4. **能保留原状态。** 改动、失败、停止和回退都有记录；不修改用户无关文件，不把低于噪声的变化判成收益。
5. **能积累可靠经验。** 成功、失败、无收益和不适用条件均可查询；原证据或适用环境变化后，旧结论会降级或撤回。

### 3.3 会话与决策的关键行为

1. 先读取项目与工作区差异，固定代码、输入、预算和授权范围。
2. 先处理合法性、生命周期、功能正确性问题，再判断是否有性能候选。
3. 缺少关键证据时选择一个有界探测；其结果必须能改变下一步。
4. 仅在符合前置条件时进入已注册实验，固定 baseline 并验证回退。
5. Advisor 接受实际 receipt；候选没有收益、质量失败或证据不足时保留原方案。
6. 从原始结果导入候选经验，经过实际复核后提高证据等级；撤回会影响后续决策。

Surface/EGL 生命周期问题首先走对应规则和业务复现，不强行映射到六条性能策略。首条 wallpaper 闭环可以包含生命周期诊断，再选择确实适用的附件、纹理或动态资源实验。

### 3.4 兼容和故障控制

- 旧 `allowed_actions` 的语义保持不变；执行能力进入明确版本的执行合同，不能往旧字段硬塞不支持的动作。
- 不信任外部路径和命令；实验从已有注册表解析，校验路径、文件哈希、产物类型和可用 runner。
- context 丢失、drawable 替换和普通 resize 分别处理；旧 epoch 的结果、fence 或句柄不能被重新使用。
- patch 在隔离目录或明确作用域内执行；保存改动前状态，只撤销本次改动，保留用户既有差异。
- root、输入、代码、质量标准、环境或关键证据不匹配时，结果不得被用来支持采用。

## 5. 六条策略、主动补采与实验质量

### 5.1 六策略逐一接入

先完成 discard、fence ring、texture/mip 三条完整链，再接 MSAA、compute、fetch。前三条必须先贯穿 Advisor 和经验导入，再扩大覆盖。

| 策略 | 实验要求 | 必须覆盖的拒绝或失败路径 |
| --- | --- | --- |
| `discard-dead-attachment` | 同一 FBO 场景比较保留与最后一次消费后 invalidate；绑定附件生命周期和 epoch | 后续仍有消费者、作用域不完整、跨代资源时拒绝；不读取已失效附件来证明正确性 |
| `fence-ring-reuse` | 固定动态更新负载，比较合法 baseline 与有界 ring/fence；记录等待、提交、质量和可得 GPU 时间 | 未完成 slot 不覆盖；超时、context 重建和旧 fence 有明确停止/重建路径 |
| `texture-mip-selection` | 固定缩放与采样序列，对照 mip/filter 候选；复用 texture-access 及质量检查 | mip 不完整、文字失真、内存超预算、负载变化后收益失效 |
| `resolve-msaa-once` | 同一多 pass 图比较重复 resolve 与合法消费边界的一次 resolve | 中间结果实际需要、format/sample 不兼容、resize 后旧附件、画质超限 |
| `compute-to-fragment` | 复用 shader-advanced，验证 compute 写入到 fragment 实际消费者之间的合法同步 | API/入口不足拒绝；按消费者核对 barrier；不靠偶发数据竞争作为唯一负控 |
| `coherent-framebuffer-fetch` | 在精确扩展支持环境中，与合法 ping-pong baseline 对照颜色/混合语义 | coherent/non-coherent 不混用；无扩展、限定反例或质量失败时走独立 fallback |

每条策略必须同时具备正式 registry 绑定、实际 GLES baseline/candidate、至少一个适用环境运行回执、质量检查、Advisor 结论、经验导入和失败路径。仅有注册或“不支持时拒绝”不算完成。支持该扩展的环境不可用时，原路径保持 BLOCKED；fallback 独立报告。

软件 GLES 结果只支持其实际验证范围；任何物理 GPU 性能结论必须有对应设备结果。现有实验范围不自动升级为硬件性能证明。[S02] [S03]

### 5.2 硬约束与偏好分开

| 输入/状态 | 行为 |
| --- | --- |
| 偏好权重 | 用于在合格候选中排序，不能抵消非法 API 或画质失败 |
| 内存、质量、延迟、热状态等硬约束 | 记录单位、采集方式、阈值来源、适用阶段；确认违反即阻止采用 |
| 能力或关键证据未知 | 提出补采或有界实验；保持“未证明可采用” |
| 正确性通过、收益未测 | `EXPERIMENT_REQUIRED` |
| 画质失败、收益不足或噪声过大 | 分别记录 QUALITY_FAIL、NO_GAIN 或 INCONCLUSIVE，保留 baseline |

具体预算由业务与设备确定，不预设通用 60/120 FPS、统一显存限额或必定提升百分比。无法可靠读取实际 GPU 内存时，把估算资源字节标为估算，不用它冒充显存测量。温度/热状态也不替代功耗。

### 5.3 next_probe 的首版范围

每次输出一个必要探测，包含 probe ID、要区分的根因、输入/前置条件、各结果的后续分支、时间/帧数/内存预算、停止原因。复用已有采集器、生命周期检查、质量 oracle 和实验入口。

验收至少覆盖：计时能力未知；driver/backend 不清；附件后续消费者未知；质量指标缺失；两份证据冲突；预算耗尽；探测失败或环境变代。探测返回后必须改变决策或明确停止，不能无限重复同一建议。

GPU 时间不可得时，保留缺失并使用能够取得的其他证据；CPU frame time 不能改名为 GPU time。不引入通用规划模型或在线自学习系统。

### 5.4 A/A、配对实验与停止条件

1. 冻结输入、代码、质量门槛、设备状态、预热、运行顺序与总预算。
2. 先做有界 A/A，估计同一 baseline 的噪声与漂移。
3. 按预注册的 AB/BA 或 ABBA 顺序和次数比较，不跑到出现正收益才停止。
4. 分开报告冷/暖启动、CPU 提交、GPU、present/交互延迟、p95/p99、资源和长期稳定；只报告实际可测指标。
5. 环境变化、计时无效、质量失败、超预算或错误资源使用时停止候选并回退。
6. 保留所有失败、无收益和混淆结果；按协议报告效应、离散程度和有效样本，不能只选择最好的一轮。

六策略声明资源读写和互斥条件；代表性组合实际比较 baseline、A、B、A+B。单项收益不能直接相加。质量未知可允许受控测量，但不能支持正式采用。

执行预算包括设备时间、存储、运行次数和 provider 消耗。已有授权范围内持续完成工作；超出授权或预算时给出具体阻塞，避免逐项重复询问。

## 6. 经验系统必须形成的行为

### 6.1 最小治理命令

以下为拟实现的命令能力，不是当前已经可调用的 CLI。

| 能力 | 输入与结果 |
| --- | --- |
| `validate` | 校验 schema、来源、哈希、适用条件、状态转换和实际证据引用 |
| `import` | 从合法 receipt 生成 CANDIDATE；保留 raw evidence，不自动宣称 VERIFIED_DEVICE |
| `query` | 按策略、workload、API、backend、driver、环境查询；区别 exact 与 related 匹配 |
| `review` | 记录真实复核者、版本、依据、适用范围和结论；不自动补造独立审核身份 |
| `retract` | 保留历史与撤回原因，使后续决策停止使用该支持性结论 |

原始证据丢失或哈希变化、上游实现改变、driver/backend 超出验证范围时，标记失效或待复核。相同 GPU 商标不代表相同适用条件。失效传播需实际经过 query→Decision→Advisor 验证。

### 6.2 50/10 的计数方式

- 至少 50 个唯一逻辑案例，至少 10 个冲突/反例是其子集；revision 不能计新案例。
- 旧 3 条案例保留 ID，经过新校验后才能纳入合格总数。
- 同根因换分辨率、GPU 名或复制日志通常仍是同一案例；如适用条件导致不同机制，必须说明为何独立。
- 分别统计规范/源码依据、软件复现、物理设备复现和明确合成的治理样例。
- 合成数据可以验证导入/撤回/匹配，不得伪称真实驱动故障；也不能用大量模板代替实际经验积累。
- 六策略的完整运行结果必须进入经验流程；业务失败、无收益和有边界的成功都可以成为经验。

如果没有足够合格材料，保持缺口，不补造。50 是前序最低义务，不意味着所有案例都必须有真机性能收益，也不允许将其表述成 50 条已验证硬件优化。

### 6.3 必须完成的一条演示

一个候选起初看起来合理；系统主动补采，发现质量超限或收益不确定；保留 baseline，保存限定反例；下一次遇到相同条件能避免再次推荐。撤回该证据后，相关判断恢复为待验证，而不是继续使用旧结论。

## 7. 四引擎、八条主线与 20 个业务工单

### 7.1 工程组织方式

采用一个共用的 Java+C++17 Android 业务壳、四个薄引擎工程，以及共享的场景输入、资产、操作脚本和证据结构。八条主线均有明确可运行入口，不要求八个独立的大工程。

| 工程入口 | 主要承载 | 必须独立验证的引擎合同 |
| --- | --- | --- |
| 自研 Android Java+C++17 壳 | G01、G04、G05、G08，G07 原生对照 | EGL/线程 owner、context/drawable generation、在途资源与宿主生命周期 |
| Cocos native GLES | G02，参与 G04/G08 | 原生 backend、batcher、遮罩、资源引用、渲染线程与状态缓存 |
| Filament Android OpenGL | G06 | Engine/View/SwapChain、asset/instance owner、材质工具链及颜色处理 |
| Godot Compatibility | G03 | 实际 renderer、材质/粒子/灯光能力、实例与场景资源生命周期 |
| Unity URP GLES | G07，B12/B16 专属子项 | URP 版本与扩展点、RenderGraph 输入、native texture 回调和状态恢复 |

四引擎均锁定实际采用的版本/commit、包锁、构建参数和 GLES backend。规划不把某个旧版本冒充最新版本；实施选择版本时核对对应官方源码/文档及实际目标能力。

共享业务输入不等于共享线程或资源所有权。WallpaperService、Activity、预览和媒体输出使用各自宿主适配，不揉成一个全局生命周期状态机。没有获准的 MAGE 项目源码时，交付称“自研 GLES 壳”；MAGE 迁移子项保持待接入。CocosAirJS/WebGL2 作为独立浏览器路径，不计为原生 GLES 引擎验收。[P01] [A01]

### 7.3 高风险业务的额外要求

**宿主和异步资源。** 明确 context、drawable、实例和 asset 的不同代际；记录 owner 和借用关系。CPU 任务取消不表示 GPU 已完成；退役资源必须等待实际合同允许的时机。共享资源不能因一个预览关闭而被另一个实例提前释放。

**媒体。** 预览允许丢弃旧帧，编码使用有界队列与声明的丢帧/节奏政策；编码慢不能无限积压。源时钟不能直接与另一时钟相减当延迟。AHardwareBuffer 路径需按实际导入和同步证据判断复制情况，不自动宣称零复制。相机输入与视频输入分别验收，不能仅用 Canvas producer 证明两者完成。

**字体与 Text3D。** 可以复用项目已有、许可合规的字体解析/整形依赖；Text3D 三角化须复用自有实现或依据公开算法原理独立实现，不直接使用、vendor 或翻译重写 `earcut.hpp`。孔洞、多轮廓和退化轮廓必须进入实际几何检查，MSDF 解码 smoke 不替代完整字体业务。

**渲染和质量。** 跨引擎对比按材料、颜色空间、几何和业务关键区域判断，不强求不同渲染器逐像素一致。HDR/SDR、temporal、DRS 分别记录能力、历史重置、质量和 fallback；不支持的设备只能证明其降级路径。

## 8. 物理设备、平台与真实 Agent 验收

### 8.1 平台验证分层

| 通道 | 必须记录 | 可证明的范围 |
| --- | --- | --- |
| 主机检查 | OS、Python/编译器、依赖锁、schema 与测试版本 | 规则、输入、契约、路径和构建逻辑 |
| 软件 GLES | renderer、API/扩展、实际 shader/场景与 oracle | 对应软件实现上的正确性；不计物理 GPU 或移动性能 |
| Android 14+ 物理设备 | SoC/GPU/driver、OS/API、ABI、实际 backend、热/电源状态和运行记录 | 对应配置的业务、生命周期与实际测量 |
| Windows ANGLE / WoA | CPU/进程 ABI、ANGLE revision、实际 D3D/Vulkan/OpenGL 等 backend、驱动和窗口路径 | 相应 Windows 组合；x64 结果不能自动覆盖 WoA |
| Embedded Linux | 板卡/driver、EGL platform、实际窗口系统与 GLES 支持 | 相应设备与呈现路径；无头软件不等于设备显示链 |

至少两类不同物理 GPU 完成规定关键场景，优先按可用资源选择 Mali 与 Adreno；PowerVR 的规则和精确适用条件继续保留，真机条款按原义务逐项执行。两类 GPU 是最低数量，不自动豁免此前要求的第三类厂商、平台或特定场景。[P01]

模拟器可以验证其覆盖的 Android 业务流程；软件后端、mock 或只编译 APK 均不能填物理 GPU 性能结果。缺 KVM、SDK、设备或扩展时登记具体阻塞；不把环境未启动写成应用渲染失败。

### 8.2 两类 Agent 协议分别报告

**正文协议：** 保留现有只注入 SKILL.md 的评测方式及局限，验证主入口内容本身能带来什么改善。

**完整项目协议：** Agent 能读取实际安装包中的 references/tools，在隔离项目中诊断、修改、构建、运行、判断及回退。记录检索到哪些文件、调用了哪些工具、实际修改和测试产物，而不是只对文字答案评分。

Off/On 使用相同实际模型配置、预算、工具能力、项目输入和评分规则，仅改变待评估技能条件。分组标签对独立评判者隐藏；模型身份、原始请求/响应、usage、失败和重试保留。正文成绩与完整 Agent 成绩不混合。[S12]

| --- | ---: | --- |
| F：v1.1.0 冻结任务 | 100 | 保持冻结 ID、题目和 rubric；独立审阅后真实 Off/On；不能用答案回填优化再冒充未接触评测 |
| N：新增旗舰任务 | ≥40 | 补齐原新增义务；与 F 分开报告，避免语义重复；按项目来源分组隔离 |
| P：项目闭环任务 | ≥25 | 是 N 的明确子集；不是另加 25 个独立仓库或额外放大总任务数 |

完整的一轮 F 对照是 200 份响应；若 N 恰为 40，新增一轮对照是 80 份响应。响应数不等于任务数，实际重复次数按冻结协议执行。F 与 N 不共享同一逻辑任务；相关变体与来源关联明确记录，不宣称无法证明的“零污染”。

每个 P 任务至少记录：原问题→可复现输入→诊断依据→实际 patch→前后对照→必要回归→真实回退/恢复验证→限制。回退只撤销本次修改，不能清除用户文件。

### 8.4 质量目标和计数

保持原评测协议的目标：该评测集上 P0 非法生成为 0、有效首次运行率至少 90%、合法控制的误报率不超过 5%。执行前固定分母、适用任务、缺失结果、重试、严重性和 oracle；失败后修复的运行不能算首次成功。[S12]

缺少响应、独立审阅或真实构建/运行证据时，不填 0 误报或 100% 成功。报告样本数量、逐条件结果、配对数量及合理不确定性；这组指标不构成对所有未来请求的保证。

在同一来源项目衍生出的任务按组隔离；调试集、训练用例、开发案例和最终验收分别标识。技能路由、经验模块、工具检索成本可进行预注册的有限消融比较；不因看见最终题目表现而临时改协议。

### 10.4 最终代码树与回执的绑定

推荐将最终 receipt 和完整 gate report 作为代码树外的 CI 产物，避免证据自身参与自身哈希：

1. 固定最终 main commit C，并记录完整 tree T。
2. CI 检出 C，计算实际依赖清单，执行或校验规定验证。
3. 在代码树外生成绑定 C/T 的 receipt、原始产物清单与独立复核索引。
4. 仓库保留 schema、验证器、义务和依赖声明；当前结果由该外部报告承载。
5. 后续把报告链接或任何变更提交回 main 会形成新 commit，须为新 main 重新生成最终报告。

历史运行可复用时，保留真实执行 commit/日期；仅当原门禁允许、相关依赖全部相同、环境和有效期仍适用，才由当前验证器记录复用依据。不能改旧 receipt 的 commit 字段冒充新运行。最终 main 的完整 CI 必须绑定最终实际 checkout；几个各自基于旧 main 的绿色 PR 不等于最终集成树通过。[A01]

### 10.5 安装、路由和包质量

- 主入口能发现 Decision、Experiment、Experience、业务与研究工具；保持已有模型路由和触发语义。

- metadata、当前候选状态、已验证范围和历史版本分开；不为通过旧断言伪造新旧版本。

安装能力检查只验证明确支持的配置，不自行增设要求用户提供凭据或安装大型服务的流程。
