## 1. 目标与发布原则

将现有专家知识型 Skill 升级为可以完成 **规范约束 → 代码生成/审查 → 编译运行 → GPU 定量诊断 → AI Agent Benchmark → 证据沉淀与持续更新** 的工程型 Skill。保留现有 GLES 3.0/3.1/3.2、GLSL ES、Android、ANGLE/Windows-on-ARM、Embedded Linux、Mali/Adreno/PowerVR 规则及触发条件，不删除旧约束；仅针对已证实的错误做精确修订。

**一次版本完整交付，多个内部工作包与 PR**：可以并行研发和独立审查，但 **所有 W0–W7 必须合并验收之后才更新版本为 v1.0.3 并发布 tag**。不得将只完成文档或某项子任务称为版本交付。缺少设备导致无法实测时，必须在报告明确标记 `BLOCKED_BY_HARDWARE`，不能伪造性能结果。

### 3.1 已核实、值得行动的线索

1. **Khronos 2026-10-25 GLES 3.0 认证条目：Vivante / Mesa etnaviv / Embedded Linux。** 对应 NXP i.MX 8M 系列和 Mesa etnaviv 驱动；给 GLES Skill 增加非 Mali/Adreno/PowerVR 的嵌入式兼容样本。注意：认证具体设备和测试配置不能代表全部 Vivante GPU。来源：https://www.khronos.org/conformance/adopters/conformant-products/opengles

3. **Android 开发文档的战略方向：Vulkan 成为主要图形 API，OpenGL ES 继续支持但不作为新特性开发主线。** 这是已存在的平台演进趋势，**不是本月新发布事件**；用于本版本的 GLES vs ANGLE vs Vulkan 决策树。来源：https://developer.android.com/games/develop/vulkan/overview
4. **ANGLE Android 驱动与不同 backend 的能力差异。** 项目文档可用于实测部署和后端矩阵；ANGLE 的 GitHub mirror 不提供按 release tag 的稳定版本列表，增量追踪应以 Chromium Git 历史和 issue/CL 为准。不能将仓库 README 的整体支持矩阵代替某个设备的能力探测。来源：https://github.com/google/angle ; https://github.com/google/angle/blob/main/doc/DevSetupAndroid.md
5. **Khronos 2026-10-08 Vulkan CTS 1.4.7.0。** 与 GLES 有关的是测试组织、能力探测与回归方法；该发布**不构成 GLES 新特性**。GLES CTS 当前独立跟踪 `opengl-es-cts-*` 标签。来源：https://github.com/KhronosGroup/VK-GL-CTS/releases ; https://github.com/KhronosGroup/VK-GL-CTS/wiki/Overview-of-releases

## 4. Android/GPU/现代渲染/验证的详细任务与验收



### W2 Android / ANGLE / EGL / 设备能力矩阵

- `CapabilitySnapshot` 的采集项：OS/API、EGL vendor/version/extensions、GL vendor/renderer/version/extensions、ANGLE backend（能可靠探测时）、扩展函数入口、格式支持、运行时限制。
- 必测：后台/前台、surface destroy/recreate、context loss、尺寸变化、multi-context、driver/backend 切换、纹理跨线程移交；区分 `EGL_BAD_SURFACE` 和 `EGL_CONTEXT_LOST`。
- Android 17/Play 政策：分类为平台政策与实际功能，不假定系统要求自动意味着设备拥有某扩展。

### W3 移动 GPU 微架构和性能基准

- 每项优化都需要设备型号、驱动、分辨率、目标场景、热状态、GPU/CPU 时序和对照 counter；不跨 GPU 泛化百分比。
- 最小场景：clear/load/store、depth/stencil invalidate、MSAA resolve、alpha discard、front-to-back、FBO switch、texture compression、half precision。
- 有利/不利结果均需记录，避免只保留成功案例。

### W4 现代移动渲染工程与示例

- 每张技术卡：适用设备/版本 → 原理 → 最小可运行 GLES 代码 → fallback → 视觉正确性测试 → 带宽/时延测量 → 官方来源。
- 重点补充运行时 HDR/WCG、AHardwareBuffer、EGLImage、texture external、PBO stream、frame pacing、编译卡顿、移动后处理组合等。

### W5 自动校验、编译与 CI

- Shader 编译与链接：`#version 300/310/320 es` 与扩展符合性，不能仅以文本正则判断全部合法性；使用真实编译/转换器和 GLES 环境。
- C++17 示例至少完成 host compile 与目标平台编译，区分编译正确、链接正确、运行正确。
- 正负测试总数目标 ≥100；每个 P0 规范错误至少 1 正例 + 1 反例；错误应显示规则 ID、依据和修正建议。

### W6 Agent Benchmark 与诊断能力

- 任务类型 `Generate / Review / Diagnose / Optimize`，至少 60 个标注案例（目标）；比较“无 Skill”与“启用 Skill”的有效性、误报、编译成功率、调试步骤、性能论证完整性。
- 性能结论必须报告基线与改进、设备信息、原始计数器和可复现命令；不能用单次 FPS 或模拟器代替真机带宽实测。


## 5. 工程执行与诊断检查清单

- 诊断场景覆盖：黑屏/闪烁、EGL 失效、FBO 不完整、GLSL 链接/精度、跨线程上传、资源泄漏、GPU 带宽、shader ALU、overdraw、CPU submit、GPU stalls、温度引起的帧耗时波动。
- 诊断输出结构：症状 → 环境快照 → 最小复现 → 确认/排除的原因 → 引用的规则 ID → 最小修复 → before/after 证据 → 回归用例。
- API 标准符合性、工具跑通、设备性能分别独立标记，不因一项通过而推断其他通过。
- 厂商工具能力需要复核现行 SDK，不能预设所有 counters 在所有 GPU 上可读。
